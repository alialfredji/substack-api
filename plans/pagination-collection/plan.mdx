# Substack pagination collection

<Callout id="pagination-outcome" tone="success">
  The implementation adds one bounded collection workflow across Substack's three real pagination mechanisms: numbered pages, opaque cursors, and archive offsets. Callers can now collect beyond the first response without inventing route parameters, while repeated pages, repeated cursors, throttled publication search, and unpaginated routes fail safely.
</Callout>

The primary user workflow is now:

```bash
substack-api collect '/profiles/search?query=ai%20engineer' \
  --limit 100 \
  --max-pages 10
```

The CLI returns a stable envelope containing `items`, `count`, `pagesFetched`, `exhausted`, and `continuation`. The same bounded behavior is available through typed client helpers for profile search, publication search, Notes feeds, archives, and category leaderboards.

<Callout id="rate-limit-stop" tone="warning">
  Retries are intentionally bounded. Reaching the final 429 stops the collection; immediately restarting the same command would defeat the cooldown and is not considered recovery.
</Callout>

## Scope and decisions

<Callout id="rest-gateway-decision" tone="decision">
  The REST gateway remains page-oriented. Its existing `page`, `cursor`, `offset`, and `limit` parameters are now documented more clearly, while aggregation lives in the typed client and CLI. This avoids duplicative `/all` HTTP endpoints and keeps the gateway a transparent proxy.
</Callout>

The release is additive and versioned as `0.2.0`. New public helpers are exported without changing existing one-page methods or response schemas. The implementation deliberately does not add pagination to reactors, comments, recommendations, categories, or post search.

## Review focus

Reviewers should concentrate on three contracts:

1. Whether `continuation` should remain a `{ parameter, value }` object for resumable CLI collection.
2. Whether throwing on repeated pages/cursors is preferable to returning a partial result marked inconclusive.
3. Whether REST aggregation endpoints are worth adding later for remote HTTP consumers; they are intentionally deferred from this release.
